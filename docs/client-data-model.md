**Status:** **Owner-authorized implementation baseline for Phase 1.** The defaults below are accepted for engineering execution without a separate researcher gate. They have **not** been reviewed or approved by the researcher; collect her feedback at the integrated MVP pilot (#12) and revise through follow-up issues.
**Contract version:** `client-model/v1` (working MVP baseline; evolve with migrations if pilot feedback changes fields).
**Inputs:** [Researcher workflow review](./researcher-workflow-review-2026-10-28.md) (confirmed facts), [Phase 1 specification](./phase-1-client-management-spec.md) (baseline proposal).

## 1. Confirmed facts vs. proposed design

The researcher confirmed the **current workflow**, not the proposed data fields. By project-owner direction, the proposed defaults now serve as the **implementation baseline** pending actual end-user feedback during the MVP pilot. This table distinguishes evidence from implementation assumptions.

| Topic | Confirmed (survey, 2026-10-28) | Working MVP default (feedback at pilot) |
| --- | --- | --- |
| Where clients come from | Work starts with a Fiverr order. | A `source` field with `fiverr`, `referral`, `direct`, `other`. Whether non-Fiverr clients exist at all is unconfirmed. |
| Repeat clients | Repeat clients receive personalized Fiverr offers with an adjusted package or price. | One client record per person, reused across engagements. Offers and orders are **not** client fields (see §6). |
| Contact channels | Fiverr messaging; email is sometimes used for repeat-client proposals. | `fiverrUsername`, `email`, a short free-text "other contact" line, and a preferred-channel choice. No phone or postal address in v1. |
| Notes | Research notes live in OneNote today. Writing client messages is a top-3 frustration. | Dated internal notes and a manual contact log on the profile (#9). No message drafting or sending. |
| Inactive clients, prospects, cancellations | Not defined. The researcher has had no late, incomplete or cancelled orders so far. | Only two stored states, `active` and `archived`. "Prospect" and "inactive" are not stored states (§5.3). |
| Confirmation before actions | The researcher answered **"Not sure"**. | Conservative: confirm archive, restore and discarding unsaved edits. No hard delete exists in Phase 1. |
| Required fields at intake | Not defined (unresolved question 2). | Only `displayName` and `source` are required. |

## 2. Client entity

A **client** is a person the researcher works for (or may work for). The record is about *identity and contact*, not about any single order or research case.

### 2.1 Fields

Legend: **R** required on create · **O** optional · **S** system-managed (never typed by the user).

| Field | Kind | Type / storage | Validation (§4) | PII class (§3) | Notes and example |
| --- | --- | --- | --- | --- | --- |
| `id` | S | UUID v4, text | Generated by the main process. Immutable. Never reused. | Internal | `3f1c…` — never shown as a "client number". |
| `displayName` | R | text | Trimmed, 1–120 characters, no control characters. | Direct identifier | "Rosa M. (Quetzaltenango line)". The researcher's own label, which need not be a legal name. |
| `source` | R | enum | One of `fiverr`, `referral`, `direct`, `other`. | Business | No preselected value proposed (see checklist Q2). |
| `sourceDetail` | O | text | ≤ 200 characters. | Personal (may name a referrer) | "Referred by a previous client". Shown when source is `referral` or `other`. |
| `fiverrUsername` | O | text | Trimmed, leading `@` removed, no spaces, ≤ 60 characters. | Direct identifier | `@fictional_buyer_01`. A public platform handle, **not** a credential or API token. |
| `email` | O | text | Trimmed, ≤ 254 characters, `local@domain.tld` shape check only. | Direct identifier | `ana.example@example.com`. Stored as typed; compared case-insensitively. |
| `otherContact` | O | text | ≤ 200 characters, single line. | Direct identifier | "WhatsApp, ask on Fiverr first". Free text keeps v1 minimal until routine channels are confirmed. |
| `preferredContactChannel` | O | enum | `fiverr`, `email`, `other`, `unspecified` (default `unspecified`). | Business | See the consistency rules in §4.2. |
| `status` | S | enum | `active` or `archived`. | Internal | Changed only by archive and restore (§5). |
| `createdAt` | S | UTC ISO-8601 text | Set once. | Internal | |
| `updatedAt` | S | UTC ISO-8601 text | Set on every successful edit, archive or restore. | Internal | |
| `archivedAt` | S | UTC ISO-8601 text or null | Non-null if and only if `status = archived`. | Internal | Cleared on restore. The history keeps the archive event (§5.4). |

**Deliberately not in v1** (candidates only if the researcher asks): legal name, phone, postal address, country or time zone, preferred language, tags, birth dates, family details, avatar or photo. Family and ancestral data belong to research cases in later phases, not to the client record.

**Stable identity rules**

- `id` is the only key other records reference. Names, emails and handles can change without breaking links.
- No field other than `id` is unique. Duplicate detection is advisory (§4.3), because two different people can share a name.
- A client is never hard-deleted in Phase 1, so an `id` can never be reused for anyone else.

### 2.2 TypeScript shape (for #5 / #6)

```ts
type ClientSource = 'fiverr' | 'referral' | 'direct' | 'other'
type ContactChannel = 'fiverr' | 'email' | 'other' | 'unspecified'
type ClientStatus = 'active' | 'archived'

interface Client {
  id: string                       // UUID v4, immutable
  displayName: string
  source: ClientSource
  sourceDetail: string | null
  fiverrUsername: string | null
  email: string | null
  otherContact: string | null
  preferredContactChannel: ContactChannel
  status: ClientStatus
  createdAt: string                // UTC ISO-8601
  updatedAt: string
  archivedAt: string | null
}

// What the renderer may send on create/edit. System fields are never accepted from the renderer.
type ClientInput = Pick<Client,
  'displayName' | 'source' | 'sourceDetail' | 'fiverrUsername' |
  'email' | 'otherContact' | 'preferredContactChannel'>
```

Optional fields are stored as `null` when blank, never as the empty string.

### 2.3 Related entity: notes and contact log (#9, proposed)

These are kept separate from the client so the profile stays small and history is append-friendly.

| Field | Kind | Notes |
| --- | --- | --- |
| `id` | S | UUID v4 |
| `clientId` | S | References `Client.id`. Restrict delete; never cascade. |
| `kind` | R | `note` (internal thought), `contact` (a message sent or received, logged by hand), `system` (archive/restore, created automatically) |
| `occurredAt` | R | Defaults to now. Editable for `note` and `contact` so the researcher can back-date a logged message. |
| `channel` | O | Only for `contact`: `fiverr`, `email`, `other` |
| `direction` | O | Only for `contact`: `inbound` or `outbound` |
| `body` | R | 1–10,000 characters. Plain text. |
| `createdAt`, `updatedAt` | S | |

The contact log is **manual record-keeping only**. Phase 1 never sends, drafts or imports messages.

## 3. Personal-data classification

| Class | Fields | Handling rules |
| --- | --- | --- |
| **Direct identifier** | `displayName`, `fiverrUsername`, `email`, `otherContact` | Stored only in the local database. Never logged, never included in error messages, crash reports, analytics, IPC rejection messages, test fixtures or screenshots (fictional values only). |
| **Sensitive free text** | Note `body`, `sourceDetail` | May contain family history, ancestry, health or immigration details about the client **and third parties**. Same rules as direct identifiers. Treat as the most sensitive data in the app, and never send it to any external service (no AI processing in Phase 1). |
| **Business metadata** | `source`, `preferredContactChannel`, note `kind`, `channel`, `direction` | Not identifying alone. Safe in aggregate counts. |
| **Internal** | `id`, `status`, timestamps | Not personal data alone. Safe in logs **as long as no identifier is logged next to them**. |

Engineering consequences:

- IPC validation errors return only the field name and a rule code (for example `{ field: 'email', code: 'invalid-format' }`), never the submitted value. This extends the existing no-echo rule in `createValidatedHandler`.
- Backups (#11) contain every class above and must be described to the researcher as personal data.

## 4. Validation rules

### 4.1 Normalization (applied before validation and storage)

- Trim leading and trailing whitespace on every text field, and collapse internal runs of whitespace in `displayName`.
- Convert blank optional fields to `null`.
- `fiverrUsername`: strip one leading `@`.
- Reject control characters (U+0000–U+001F, U+007F) in single-line fields.
- Do not change case or accents in stored values. Those are applied only in comparison keys (§4.3).

### 4.2 Field and cross-field rules

| Rule | Severity | Message (plain language) |
| --- | --- | --- |
| `displayName` missing | Error, blocks save | "Add a name so you can find this client later." |
| `displayName` > 120 characters | Error | "Keep the name under 120 characters." |
| `source` missing | Error | "Choose where this client came from." |
| `email` shape invalid | Error | "This email address doesn't look complete." |
| `fiverrUsername` contains spaces | Error | "Fiverr usernames don't contain spaces." |
| Preferred channel is `email` with no email | Error | "Add an email address, or choose a different preferred contact method." |
| Preferred channel is `fiverr` with no username | Warning, allows save | "No Fiverr username yet. You can add it later." |
| Preferred channel is `other` with no other contact | Warning | "Add a note on how to reach this client." |
| No contact field filled at all | Info | "No contact details yet. That's fine, you can add them later." |

The main process re-runs every rule. Renderer checks are a convenience only.

### 4.3 Duplicate advisory (#10)

Run on create and on edit, against **all** clients, archived ones included.

| Signal | Comparison key | Strength |
| --- | --- | --- |
| Same email | lower-cased | Strong |
| Same Fiverr username | lower-cased, `@` stripped | Strong |
| Same display name | Unicode NFD, accents removed, lower-cased, whitespace collapsed | Possible |

When there is a match, the save is **paused, not blocked**. The researcher sees each match (name, status, matching signal) with three choices: **Open existing** (or **Restore existing** if archived), **Save as new client anyway**, or **Go back**. This handles a returning client who was archived without creating a second identity.

## 5. Lifecycle

### 5.1 States and transitions

```
            create
              │
              ▼
  ┌─────────────────────┐   archive (confirm)   ┌─────────────────────┐
  │       active        │ ────────────────────▶ │      archived       │
  │ editable, in default│                       │ read-only, hidden   │
  │ directory view      │ ◀──────────────────── │ from default view   │
  └─────────────────────┘   restore (confirm)   └─────────────────────┘
        ▲      │
        └──────┘ edit
```

"Restored" is a transition, not a third state. A restored client is simply `active` again, with the same `id`, notes and links.

| Action | Allowed from | Confirmation | Effect |
| --- | --- | --- | --- |
| Create | — | No (duplicate advisory may pause it) | New `id`, `status = active`, timestamps set. |
| Edit | `active` | Only to discard unsaved changes | Updates input fields and `updatedAt`. `id` never changes. |
| Archive | `active` | **Yes**, and the dialog says nothing is deleted | `status = archived`, `archivedAt = now`, adds a system note. |
| Restore | `archived` | **Yes** (lightweight) | `status = active`, `archivedAt = null`, adds a system note. |
| Add note or contact entry | `active` | No | Appends to history. |
| Hard delete, merge, bulk actions | — | — | **Not in Phase 1.** |

### 5.2 Editing archived clients (proposed: read-only)

Archived profiles are read-only, including notes. The researcher restores first and then edits. This keeps the "archived" meaning simple and prevents accidental changes to records she thought were put away. *Alternative:* allow edits while archived. (Checklist Q5.)

### 5.3 Prospective and inactive clients (proposed: not stored states)

- **Prospect** (someone who has asked but not ordered): an ordinary `active` client. When orders exist (Phase 2), "no orders yet" can be shown as a derived label, without a status field that could drift.
- **Inactive** (no recent work): not stored either. Later it can be derived from the latest note or order date. The researcher can archive anyone she no longer wants in the default view.
- Archiving is the only "put away" action and is always reversible.

(Checklist Q4.)

### 5.4 History and audit

Archive and restore each add a `system` note ("Archived on 12 Mar 2026") to the client's history. No separate audit table is proposed for Phase 1.

### 5.5 Directory defaults (#7)

- Default view: `active` only. The status filter offers Active, Archived, All.
- Source filter: any combination of the four sources.
- Search (accent- and case-insensitive substring) matches `displayName`, `fiverrUsername`, `email` and `otherContact`. Notes are **not** searched in Phase 1.
- Sort options: Name A–Z (default; locale-aware collation that ignores accents, ties broken by `createdAt`, then `id`), Recently updated, Recently added.

## 6. Repeat clients and future relationships

Confirmed: repeat clients come back through personalized Fiverr offers. Proposed model:

```
Client 1 ───< Engagement (Phase 2: a Fiverr order or custom offer)
                 │  package, negotiated price, deadline, external order reference
                 └──< ResearchCase (Phase 2+: goal, tree, sources, report)
Client 1 ───< ClientNote (Phase 1, #9)
```

- A repeat purchase is a **new engagement on the same client**, never a new client record.
- Until engagements exist, the researcher records an order or offer reference in a note (for example "Custom offer sent, Basic package, adjusted price"). Phase 1 does **not** invent order fields on the client.
- Every child table references `Client.id` with `ON DELETE RESTRICT`. Archiving a client never archives or deletes its engagements automatically; the Phase 2 archive rules for open cases are still to be decided.
- Whether one client can have several open orders, and one order several cases, is unresolved (survey question 3). The one-to-many shapes above allow both.
