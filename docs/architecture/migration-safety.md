# Migration safety (#248)

Design summary; the operator steps are in [../operations/database-migration.md](../operations/database-migration.md).

- `src/main/database/schema-preflight.ts`: `inspectProfile(userDataDir, latest)` classifies a profile as `fresh`, `current`, `migration-required`, `too-new` or `unsafe(reason)` without creating, opening read-write or modifying anything. The version is the *effective* page-1 header: `wal-reader.ts` walks a non-empty `-wal` with plain file reads (frame salts and cumulative checksums, only up to the last valid commit frame; never SQLite, so never a `-shm`) and takes the last committed copy of page 1, else the main file's header (`user_version` at offset 60, `application_id` at offset 68). A log with an invalid, unknown or truncated header, or a log beside an empty main file (SQLite would discard it), is `unsafe(wal-unreadable)`.
- Residue is checked first and fails closed: a `tracing-guatemala.sqlite.replaced-*` file (interrupted restore) or `maintenance/migration-in-progress.json` (interrupted migration). A profile is `fresh` only if the database is absent (or 0 bytes with no log), there is no `profile-initialized.json` in the profile root, `data/` is empty and the root's `backups/` and `uploads/` are absent or empty; anything else without a database is `unsafe(missing-database)`. The marker is written by `openAppDatabase` (new profile, or a current one that lacks it) and by the maintenance command.
- `openAppDatabase` runs the preflight before `mkdir`. Only `fresh` and `current` open; the rest throw `MigrationRequiredError`, `DatabaseTooNewError` or `DataProfileUnsafeError` without opening read-write. The old in-place upgrade with a `VACUUM INTO` copy was removed from normal open. `migrate()` itself is unchanged and is used by the maintenance command, restore staging and tests. The `migrations` option is an in-code test seam; no environment variable, flag or file selects it.
- `AppData.restoreBackup` still migrates only its staging copy, then swaps. While the restore runs, its own `.replaced-*` file is passed to the preflight as a known leftover; after a crash the next start sees it as `restore-interrupted`.
- `src/server/maintenance/migrate-database.ts` upgrades a verified copy and swaps it in under the Live folder lock: read-only integrity check and table fingerprints (`manifest.ts`), marker, verified snapshot, staging migration with an additive-content check, swap, strict verify, local record. `src/server/main.ts` exposes it as `--migrate-database` / `--revert-migration` and never starts the server in that mode.
- Console output and errors carry versions, counts, error codes and names relative to the data folder; never absolute paths or row content.
- With `TG_TEST_HOOKS=1` the web host runs only on a synthetic test profile: the real path is inside the system temp folder, the folder holds `tg-synthetic-test-profile` with its exact fixed content (`markSyntheticTestProfile`), and it is not the default Live or desktop folder. Anything else is refused. The maintenance command also probes for other open connections (`BEGIN EXCLUSIVE` without waiting) and re-checks the file just before the swap; these are evidence, not proof (see the runbook).
