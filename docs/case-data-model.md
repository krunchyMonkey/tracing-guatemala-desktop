# Research case data model and API contract (#14)

**Version:** `case-model/v1` (2026-10-29)
**Status:** **Owner-authorized provisional design**, input to #15. It implements the defaults in [`case-lifecycle/v1`](./case-lifecycle.md) (#13). Nothing here is researcher-approved; feedback is collected at #21.
**Builds on:** [`client-model/v1`](./client-data-model.md), SQLite storage and migrations (#5), backup/restore (#11), the web-first runtime and typed local API (#110, [web-first-runtime.md](./architecture/web-first-runtime.md)).

All examples are fictional.

## 1. Entities

```
clients 1 ──── * research_cases 1 ──── * case_events
   │                  │
   │                  └── (later) case brief items #17, journal #18, tasks #19, time entries #109
   └── client_notes (Phase 1, unchanged)
```

- **`research_cases`**: one row per case. A case belongs to exactly one client, forever.
- **`case_events`**: an append-only history of state and archive changes (lifecycle §3.1). #15 writes it, and #16 shows it as the case timeline. It replaces "system notes" for cases, so client notes stay about communication.
- No other tables in this version. Later child entities follow the keying rules in §7 and arrive with their own features and migrations.

## 2. TypeScript shapes (`src/shared/case-model.ts`, created by #15)

```ts
export type CaseState = 'intake' | 'active' | 'waiting' | 'delivered' | 'closed'
export const CASE_STATES: readonly CaseState[] = ['intake', 'active', 'waiting', 'delivered', 'closed']
export const OPEN_STATES: readonly CaseState[] = ['intake', 'active', 'waiting']

export const CASE_TITLE_MAX = 160
export const CASE_GOAL_MAX = 4_000
export const ORDER_REFERENCE_MAX = 100

export interface ResearchCase {
  id: string                 // UUID v4, generated by the host, immutable
  clientId: string           // FK → clients.id, immutable
  title: string              // 1–160, single line
  goal: string | null        // requested outcome, client's words, ≤ 4000, multi-line
  orderReference: string | null // ≤ 100, single line, plain text
  dueDate: string | null     // 'YYYY-MM-DD' local calendar date, no time zone
  state: CaseState
  stateChangedAt: string     // UTC ISO-8601; = createdAt until the first change
  createdAt: string          // UTC ISO-8601
  updatedAt: string          // UTC ISO-8601; any edit, state change, archive or unarchive
  archivedAt: string | null  // UTC ISO-8601 when archived; null otherwise
}

/** What the browser may send. Strict: id, clientId, state and timestamps are never accepted here. */
export interface CaseInput {
  title: string
  goal: string | null
  orderReference: string | null
  dueDate: string | null
}

export type CaseEventKind = 'created' | 'state' | 'archived' | 'unarchived'
export interface CaseEvent {
  id: string
  caseId: string
  kind: CaseEventKind
  fromState: CaseState | null // 'state' only
  toState: CaseState | null   // 'created' (= 'intake') and 'state'
  occurredAt: string          // UTC ISO-8601
}

export type CaseField = keyof CaseInput
export type CaseIssueCode = 'required' | 'too-long' | 'invalid-characters' | 'invalid-format' | 'invalid-date'
/** Like ClientIssue: a field and a code, never the submitted value. */
export interface CaseIssue { field: CaseField; code: CaseIssueCode }

export interface CaseQuery {
  clientId: string | null                  // null = all clients
  archived: 'active' | 'archived' | 'all'  // the case's own archive flag
  states: CaseState[]                      // empty = any state
  text: string                             // accent/case-insensitive match on title and order reference
  sort: 'due' | 'updated' | 'created' | 'title'
}

export type CaseMutationResult =
  | { ok: true; case: ResearchCase }
  | { ok: false; reason: 'invalid'; issues: CaseIssue[] }
  | { ok: false; reason: 'not-found' }
  /** The client is archived (create), or the case/client is archived (any change). */
  | { ok: false; reason: 'client-archived' | 'wrong-status' }
  /** The state change isn't in the transition matrix (includes "to the same state"). */
  | { ok: false; reason: 'invalid-transition' }
```

`case` is a reserved word only as a statement, so it is valid as a property name. #15 may rename it to `researchCase` if lint or readability suggests it, but must do so everywhere at once.

## 3. Normalization and validation (`checkCase`, shared)

Normalization runs first, the same way in the browser (for instant feedback) and in the host (authoritative):

| Field | Normalization | Errors |
| --- | --- | --- |
| `title` | Trim; collapse internal whitespace to single spaces | empty → `required`; > 160 → `too-long`; control characters → `invalid-characters` |
| `goal` | Trim; empty → `null`; keep line breaks (normalize `\r\n` to `\n`) | > 4000 → `too-long`; control characters other than `\n` and `\t` → `invalid-characters` |
| `orderReference` | Trim; empty → `null` | > 100 → `too-long`; control characters → `invalid-characters` |
| `dueDate` | Trim; empty → `null` | not `YYYY-MM-DD` → `invalid-format`; not a real calendar date (e.g. `2026-02-30`) → `invalid-date` |

Due dates have **no range rule**: a past due date is valid (an order entered late). "Overdue" is computed for display only (lifecycle §6), against **local today** as `YYYY-MM-DD` string comparison, never through `Date` + UTC.

Raw-payload bounds in the zod contract only stop oversized requests: title ≤ 1,000, goal ≤ 8,000, orderReference ≤ 1,000, dueDate ≤ 64. The rules above produce typed issues, not rejections, like `client-model/v1`.

## 4. State transitions (`canTransition`, shared)

```ts
export const CASE_TRANSITIONS: Record<CaseState, readonly CaseState[]> = {
  intake: ['active', 'waiting', 'closed'],
  active: ['waiting', 'delivered', 'closed'],
  waiting: ['active', 'delivered', 'closed'],
  delivered: ['active', 'closed'],
  closed: ['active']
}
/** Transitions the UI must confirm (lifecycle §3.1 ⚠). */
export const CONFIRMED_TRANSITIONS = new Set(['intake>closed', 'active>delivered', 'active>closed', 'waiting>delivered',
  'waiting>closed', 'delivered>active', 'delivered>closed', 'closed>active'])
```

Confirmation is a UI rule. The host enforces only the matrix, the archive rules and the client rule.

**Order of checks for every change:** case exists (`not-found`) → client active (`wrong-status`; for create, `client-archived`) → case not archived (`wrong-status`, except unarchive) → transition allowed (`invalid-transition`) → input valid (`invalid`). The order is deterministic, so tests and UI messages are stable.

## 5. SQLite schema: migration 3 (forward-only)

Added as `migrations[2]` (`version: 3`, `name: 'research_cases'`) in `src/main/database/migrations.ts`. The SQL is literal so the test suite can pin it:

```sql
CREATE TABLE research_cases (
  id TEXT PRIMARY KEY NOT NULL CHECK (length(id) = 36),
  client_id TEXT NOT NULL REFERENCES clients (id) ON DELETE RESTRICT,
  title TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 160),
  goal TEXT CHECK (goal IS NULL OR length(goal) BETWEEN 1 AND 4000),
  order_reference TEXT CHECK (order_reference IS NULL OR length(order_reference) BETWEEN 1 AND 100),
  due_date TEXT CHECK (due_date IS NULL OR due_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  state TEXT NOT NULL DEFAULT 'intake'
    CHECK (state IN ('intake', 'active', 'waiting', 'delivered', 'closed')),
  state_changed_at TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  archived_at TEXT
) STRICT;

CREATE INDEX research_cases_client_idx ON research_cases (client_id, updated_at);
CREATE INDEX research_cases_due_idx ON research_cases (due_date) WHERE due_date IS NOT NULL;

CREATE TRIGGER research_cases_no_delete BEFORE DELETE ON research_cases
BEGIN
  SELECT RAISE(ABORT, 'research cases are never deleted');
END;

CREATE TRIGGER research_cases_immutable_keys BEFORE UPDATE OF id, client_id ON research_cases
BEGIN
  SELECT RAISE(ABORT, 'case id and client are immutable');
END;

CREATE TABLE case_events (
  id TEXT PRIMARY KEY NOT NULL CHECK (length(id) = 36),
  case_id TEXT NOT NULL REFERENCES research_cases (id) ON DELETE RESTRICT,
  kind TEXT NOT NULL CHECK (kind IN ('created', 'state', 'archived', 'unarchived')),
  from_state TEXT CHECK (from_state IS NULL OR from_state IN ('intake', 'active', 'waiting', 'delivered', 'closed')),
  to_state TEXT CHECK (to_state IS NULL OR to_state IN ('intake', 'active', 'waiting', 'delivered', 'closed')),
  occurred_at TEXT NOT NULL,
  CHECK ((kind = 'state') = (from_state IS NOT NULL)),
  CHECK ((kind IN ('created', 'state')) = (to_state IS NOT NULL))
) STRICT;

CREATE INDEX case_events_case_idx ON case_events (case_id, occurred_at);

CREATE TRIGGER case_events_append_only_update BEFORE UPDATE ON case_events
BEGIN
  SELECT RAISE(ABORT, 'case events are append-only');
END;

CREATE TRIGGER case_events_append_only_delete BEFORE DELETE ON case_events
BEGIN
  SELECT RAISE(ABORT, 'case events are append-only');
END;
```

Design notes:
- **No cascade anywhere** (`ON DELETE RESTRICT` plus delete triggers). Clients are never deleted (Phase 1 trigger), so cases can't be orphaned. `PRAGMA foreign_keys = ON` is already set on every connection (`configureConnection`).
- **Archive is only `archived_at`**: there is no separate status column for cases, unlike clients, so archive can't drift from progress. "Archived" ⇔ `archived_at IS NOT NULL`.
- **Client-archive rules are enforced in the repository**, not in triggers. Reading the client's status inside the same `BEGIN IMMEDIATE` transaction as the write closes the race.
- **Portability (later PostgreSQL):** UUID text keys, ISO-8601 UTC text timestamps, `YYYY-MM-DD` text dates and enum-like `CHECK`s all map directly (`uuid`, `timestamptz`, `date`, `CHECK`/enum). There is no SQLite-only behaviour beyond `STRICT` and triggers, which have Postgres equivalents. No ORM.
- Every state change, archive and unarchive updates `research_cases` **and** inserts one `case_events` row in **one transaction**. `created` is written in the same transaction as the insert.

## 6. Migration, backup and rollback plan

- **v2 → v3** is additive: two new tables, no change to `clients` or `client_notes`. Before upgrading an existing database, `openAppDatabase` already writes a `VACUUM INTO` copy to `data/pre-migration/…v2….sqlite` (#5). The migration runs in a `BEGIN IMMEDIATE` transaction; on failure the database stays at v2 (`MigrationFailedError`) and the app refuses to start rather than run half-migrated.
- **Rollback** is forward-only by design: there are no down migrations. To roll back, stop the app and put the `pre-migration` copy back (documented in #117's recovery guide). An older app opening a v3 database refuses with `DatabaseTooNewError` and changes nothing.
- **Backups:** cases and events are in the same database file, so `createBackup` (`VACUUM INTO`) includes them automatically.
  - Restoring a **v2 backup** into a v3 app migrates the staged copy to v3 before swapping (`restoreBackup` already calls `migrate`), giving zero cases.
  - Restoring a **v3 backup** into a v2 app is refused as `too-new`.
  - `BackupSummary` keeps `clients` and `notes`. #15 adds `cases` as an optional count, used only where shown, after checking `inspectBackup` handles a missing table (counts 0, like `client_notes` today).
- **Desktop app:** Electron shares `migrations.ts`, so opening a desktop profile with a v3-aware build would migrate it too (with its pre-migration copy). Desktop is paused, and the web host never opens the desktop DB (#110). If the owner releases a desktop build later, this migration ships with it like any other.
- **Explicit test inputs for #15:** a real v2 database built through migrations 1–2 with fictional clients, notes and an archived client. Then migrate to v3 and assert clients and notes are byte-identical, cases are empty, and `foreign_key_check` is empty. Also: a v2 backup file restored into a v3 profile; a v3 backup rejected by a v2-only migration list as `too-new`; and an injected failure of migration 3 leaving the database at v2.

## 7. Keying rules for later child entities (#17, #18, #19, #109)

Each later table:
1. has its own UUID `id` and a required `case_id REFERENCES research_cases (id) ON DELETE RESTRICT`, with no client column of its own (the client comes from the case, so they can't disagree);
2. is read and written **only** through repository methods that take `(caseId, childId)` and filter `WHERE id = ? AND case_id = ?`, the same isolation pattern as `NoteRepository`;
3. checks the case is writable (exists, not archived, client active) in the same transaction as the write;
4. is append-only or soft-updated. There is no hard delete unless that feature's own spec allows one with confirmation;
5. adds its own forward-only migration when its feature lands (no empty placeholder tables now).

## 8. API contract (local web host, #110)

New `callable` entries on `POST /api/v1/call/<name>`, with zod contracts in `src/main/contracts.ts`, the same `AppDataApi` methods in `liveApi.ts`, and in-memory parity in `demoApi.ts`. There are no new Electron IPC channels (desktop is paused); the shared contract keeps that door open.

| Call | Args | Result |
| --- | --- | --- |
| `listCases` | `[CaseQuery]` | `ResearchCase[]` |
| `getCase` | `[caseId]` | `ResearchCase \| null` |
| `listCaseEvents` | `[caseId]` | `CaseEvent[]`, newest first; `[]` for an unknown case |
| `createCase` | `[clientId, CaseInput]` | `CaseMutationResult` (new cases start in `intake` with a `created` event) |
| `updateCase` | `[caseId, CaseInput]` | `CaseMutationResult` |
| `setCaseState` | `[caseId, CaseState]` | `CaseMutationResult` |
| `archiveCase` | `[caseId]` | `CaseMutationResult` (`wrong-status` if already archived) |
| `unarchiveCase` | `[caseId]` | `CaseMutationResult` (`wrong-status` if not archived) |

Validation boundary:
- **Browser:** runs `checkCase` for inline messages and hides disallowed transitions. Never trusted.
- **Host:** strict zod tuple (unknown keys such as `state`, `id` or `clientId` inside `CaseInput` are rejected as `invalid-arguments`). The repository then re-runs `checkCase`, the transition matrix and the archive rules. Results are validated against the result schema before sending. Errors carry codes only; logs carry no values (#110 rules).
- **Client archive UX:** `archiveClient` is unchanged. The client archive dialog may call `listCases({ clientId, archived: 'active', states: OPEN_STATES, … })` to show the warning count (lifecycle §5.2).

## 9. Test matrix for #15 (and #16 E2E)

| Area | Cases |
| --- | --- |
| Validation | each field rule and code; normalization (trim, whitespace, empty → null, `\r\n`); real-date check incl. leap years (`2028-02-29` ok, `2026-02-29` invalid) |
| Transitions | every pair in the 5×5 matrix (allowed vs `invalid-transition`), same-state rejected, one event per accepted change, none for rejected |
| Archive | archive/unarchive in each state keeps state; archived case refuses update/state change; double archive/unarchive → `wrong-status` |
| Client rules | create for archived client → `client-archived`; any change to a case of an archived client → `wrong-status`; after client restore, changes work; archiving a client changes no case row |
| Orphans and keys | insert with unknown `client_id` fails (FK); `DELETE` on cases/events fails (triggers); `UPDATE id/client_id` fails; event update/delete fails |
| Isolation | `listCases({ clientId: A })` never returns B's cases; `getCase`/`listCaseEvents` with another case's id only returns that case's own data; no API takes a client id together with a child id without checking they match |
| Migration | v2 → v3 with data (clients/notes unchanged, `foreign_key_check` empty, pre-migration copy written); failure leaves v2; `too-new` for v4 |
| Backup | v3 backup round-trip keeps cases and events; v2 backup restores into v3 with zero cases; restore failure rollback keeps cases |
| HTTP | strict args (extra keys → 400), not-signed-in/CSRF/Origin as #110, no values in errors |
| Demo parity | the in-memory demo implements the same rules (shared `checkCase`/`CASE_TRANSITIONS`) and never touches the API |
